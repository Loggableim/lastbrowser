# Local-AI Runtime Distribution and Licensing Follow-up

**Review date:** 2026-10-05  
**Scope:** Read-only audit of `docs/independent-handoff-local-ai.md`, the pinned `b11377-cpu` runtime notices, `runtime/local_ai/notices.py`, the runtime-notice UI, and current official vendor/upstream sources. No download, signature/system change, build, test run, product edit, manifest/gate change, or legal conclusion was made.

## Findings

### Microsoft CRT: VS 18/Visual Studio 2026 references replace the 2022 links

The prior handoff identifies the installed origin as Visual Studio **18 Community**, toolset `14.51.36231`, package `Microsoft.VC.14.51.CRT.Redist.X64.base,version=14.51.36247`, and the three CRT files under `VC\Redist\MSVC\14.51.36231\x64\Microsoft.VC145.CRT`. That pairing is consistent with the current Microsoft Visual Studio 2026 redistribution list, which names the VC145 runtime and permits unmodified files under `VC\redist`, subject to the applicable Visual Studio license terms. The linked Visual Studio 2022 pages in the old handoff and in the `THIRD-PARTY-NOTICES.txt` CRT section are stale for this toolset. The current reference is [Visual Studio 2026 and later redistribution](https://learn.microsoft.com/en-us/visualstudio/releases/2026/redistribution); it explicitly conditions distribution on a validly licensed VS copy and its license terms, and excludes `debug_nonredist` directories.

I independently read the three DLLs already in the runtime bundle. Each has file version `14.51.36247.0`; SHA-256 and size match the handoff. `Get-AuthenticodeSignature` reports valid signatures from `CN=Microsoft Windows Software Compatibility Publisher, O=Microsoft Corporation, L=Redmond, S=Washington, C=US`. This verifies the current packaged bytes’ signature and version, not their original filesystem path or the operator’s license. The handoff’s stated local source path/package identity remains reported provenance until backed by a retained source receipt or independently checked origin files.

`REDIST-MSVC.txt` is the byte-identical 190-byte Microsoft `Redist.txt` pointer, not the complete license terms or a copy of the current redistribution list. `LICENSE-vc-redist.txt` clearly separates that original text from project-authored integration notes; it must continue to be labeled as project documentation. The same `THIRD-PARTY-NOTICES.txt` currently calls these “2015-2022 Redistributable” files and links to the 2022 list/EULA. That user-facing entry should be corrected in a later authorized product/docs change to the VC v14 / Visual Studio 2026 references.

Microsoft’s current [Community usage page](https://visualstudio.microsoft.com/vs/community/) says individuals may use Community for their own free or paid apps; organizations may use it without a user cap for classroom learning, academic research, and contributing to open source; other scenarios allow up to five users at non-enterprise organizations, while enterprise organizations (more than 250 PCs **or** more than USD 1 million annual revenue) cannot use it outside the listed scenarios. The official [Visual Studio license directory](https://visualstudio.microsoft.com/license-terms/) now lists both Visual Studio Community 2026 and Microsoft Visual C++ V14 Redistributable and Runtime 2026. The applicable Community EULA is linked there as a vendor-hosted document.

The missing fact is the **actual licensee/operator and qualifying use scenario** for the Community installation used to produce these binaries. Neither file hashes, Microsoft signatures, an installed VS edition, nor the general Community page establish that fact. Do not infer it from this machine or this review. A factual confirmation of the licensee/use path, plus the exact applicable EULA/list and immutable source/hash/version evidence, is the minimum useful closure package. If those ordinary facts establish eligibility, this audit found no basis for inventing a mandatory separate formal-lawyer sign-off step. If they do not, use a properly licensed toolset/source or remove the bundled CRT-dependent runtime.

The current `LicensedRedistInput` contract is a **staging evidence shape**, not proof of authority: it requests a pinned official `vc_redist.x64.exe`, the original license/list, signature evidence, redistribution-authority evidence and minimum-toolset evidence; its inspector hashes staged bytes and intentionally returns `signatureVerified`, `redistributionAuthorityVerified`, `minimumToolsetVerified`, and `installAllowed` as false. The already bundled CRTs are reported as copied from the Visual Studio `VC\Redist` tree, not extracted here from a separately staged redistributable installer. Resolve which exact source artifact is being used before treating that installer-specific contract as the only possible provenance route.

### Open-source notice bytes are present; equivalence and useful source links are not established

The runtime contains `LICENSE-llama.cpp`, `LICENSE-LLVM-OpenMP`, `embedded-notices.json`, and `THIRD-PARTY-NOTICES.txt`. A local read-only check confirmed that the embedded LLVM and llama.cpp notice bodies match their corresponding standalone license files; every embedded notice’s recorded byte count/SHA matches; the extracted notice set contains LLVM OpenMP, llama.cpp, jsonhpp, BoringSSL, and cpp-httplib. The top-level notice asset also has a separate Microsoft CRT section.

That establishes pinned local text, not equivalence to each dependency’s exact source revision. `embedded-notices.json` explicitly has `sourceLicenseEquivalenceVerified: false`, and its `sourceRevision` identifies llama.cpp only. No exact source revision for the embedded LLVM OpenMP, BoringSSL, jsonhpp, or cpp-httplib text is recorded here. The [LLVM project license](https://github.com/llvm/llvm-project/blob/main/LICENSE.TXT) identifies Apache-2.0 with LLVM exceptions; the [BoringSSL license](https://github.com/google/boringssl/blob/main/LICENSE) includes Apache-2.0 redistribution terms and its support-code notice; [nlohmann/json’s MIT license](https://github.com/nlohmann/json/blob/develop/LICENSE.MIT) and [cpp-httplib’s license](https://github.com/yhirose/cpp-httplib/blob/master/LICENSE) are available from their upstream repositories. These upstream pages are useful references but mutable branches do not prove the exact dependency bytes in release `b11377`. The [llama.cpp b11377 release](https://github.com/ggml-org/llama.cpp/releases/tag/b11377) and pinned source revision should be used to derive per-component immutable source references in a later review. The pinned llama.cpp source page could not be independently parsed during this audit; no equivalence assertion is made from the moving upstream pages.

There is a concrete UI attribution defect: `notices.py` assigns the same `https://github.com/ggml-org/llama.cpp/releases/tag/b11377` `source_url` to every component. `LocalAiRuntimeNotices.tsx` renders each as a clickable “source” link, so LLVM OpenMP, BoringSSL, jsonhpp, and cpp-httplib all point to llama.cpp. The renderer presents labels and links only; it does not expose the full bundled notice text. `THIRD-PARTY-NOTICES.txt` exists inside the runtime package, but this audit found no user-facing viewer/link to that file. Therefore `complete-source-linked-and-ui-license-equivalence` remains an accurate open prerequisite. A minimal future correction is per-component immutable upstream URLs/revisions plus a readable, user-accessible copy of the packaged notices; then compare source texts at those pins and record the result. This is a concrete technical/content follow-up, not a requirement for a general formal legal-review ceremony.

The open-source references above include: LLVM’s [license text](https://github.com/llvm/llvm-project/blob/main/LICENSE.TXT), BoringSSL’s [license text](https://github.com/google/boringssl/blob/main/LICENSE), nlohmann/json’s [MIT license](https://github.com/nlohmann/json/blob/develop/LICENSE.MIT), cpp-httplib’s [MIT license](https://github.com/yhirose/cpp-httplib/blob/master/LICENSE), and llama.cpp’s [pinned release page](https://github.com/ggml-org/llama.cpp/releases/tag/b11377). Current-branch references are not immutable evidence for the bundled historical dependency versions.

### `execution_unavailable: true` is scoped to preparation metadata

In `notices.py`, `NoticeSummary.execution_unavailable` is nested inside `PreparedRuntimeSetupManifest`, whose contract is explicitly `available: false`, `execution_unavailable: true`, `skip_available: true`, and `existing_provider_available: true`. The host returns that manifest as an optional field on the runtime **inspect** response; it is not the separately returned `capability` response or an assertion that all Local-AI inference is unavailable. Runtime inspect also carries the manager’s handles. Thus this literal describes the unqualified bundled-runtime setup/preparation DTO and does not itself disable an individually qualified model or an existing provider. No change is indicated by this audit.

## Evidence boundary and smallest remaining items

Already evidenced in the current checkout: the three packaged Microsoft DLLs’ bytes, file versions, and valid Microsoft signatures; the original short Microsoft `Redist.txt` pointer; the current public VS 2026 REDIST rules; hash-pinned bundled open-source notice texts; local equality of the standalone llama.cpp/LLVM license bodies to their embedded copies; and the fact that runtime execution, MSVC closure and source/UI equivalence flags remain false.

Still needed to close the distribution questions: (1) identify the actual VS 18 Community licensee and attest the applicable individual/organization/use scenario; (2) retain exact source-package/origin evidence for the three CRT files and the edition-specific applicable license/list, without assuming the host’s license; (3) correct the 2022-era CRT links/label in the packaged third-party notice; (4) pin and compare the four non-llama upstream license sources at exact dependency revisions, and expose the full notices to users with accurate per-component source links. The existing artifacts do not prove a clean Windows loader test; this review made no such inference and did not run the clean Windows VM/Sandbox procedure.

No files under the product runtime, manifests, tests, gates, or UI were changed. No full test, build, packaging, signature mutation, runtime execution, or download was performed.
