# Issue #170: gratis Chat auf Windows

Stand: 26. November 2026. Issue #170 fordert eine gemessene Windows-Chat-Runde ohne Nutzer-API-Schlüssel. Die Drafts #161, #165, #167 und #168 existieren bereits; diese Notiz ersetzt keine Abnahme und legt keinen weiteren PR an.

## Beobachtungen

- Der separat gebaute Windows-Payload `goal-local-test-r6-20261126/win-unpacked` enthält unter `resources/services/sidekick/vendor/opencode` keinen gebündelten offiziellen OpenCode-Client. Das belegt den Inhalt dieses Test-Payloads, nicht aller Installationen oder des Store-Pakets.
- `package:linux` führt `stage-opencode-client.mjs` aus; die aktuellen Windows-Paketbefehle und der Store-Payload-Builder rufen diesen Schritt nicht auf. Das Staging-Skript kann nur einen bereits vorhandenen Client kopieren und fällt andernfalls auf OpenRouter zurück. Ob ein extern installierter Client auf einem anderen Rechner verfügbar ist, bleibt offen.
- `free_default_choice()` wählt ohne gefundenen Client `openrouter/free`. Ein direkter Test am 26. November mit einer synthetischen Kurzfrage, Modell `openrouter/free`, ohne Authorization-Header und ohne Schlüssel erhielt **HTTP 401**. Es wurde nur der Status protokolliert. Dies bestätigt den im Entwurf #161 beschriebenen Fehler zum Testzeitpunkt; eine Änderung der Anbieterbedingungen bleibt möglich.
- Ein erfolgreicher öffentlicher Widevine-Test und die allgemeinen Windows-Smokes belegen keine OpenCode-Chat-Antwort. Die Python-Tests des freien Chatpfads arbeiten mit Fixtures beziehungsweise simulierten Servern.

## Offen

Eine belastbare Lösung braucht einen auf Windows verfügbaren offiziellen Client oder einen anderen tatsächlich schlüssellosen und kostenfreien Pfad, einschließlich geprüfter Herkunft, Lizenz, Packaging und Fehlerbehandlung. Danach sind im frischen Windows-Profil eine echte Chat-Runde und ein Quickchat zu messen; zusätzlich ist die endgültige Store-Paketvariante zu prüfen. Ohne diesen Nachweis bleibt #170 offen. Es wurde kein unbekannter Client in das Paket übernommen und kein Nutzerkonto oder Schlüssel verwendet.

## Offizieller Client im isolierten Windows-Profil

Ein weiterer Test verwendete den offiziellen Windows-x64-Baseline-Client [OpenCode v2.4.2](https://github.com/anomalyco/opencode/releases/tag/v2.4.2). Der direkte Aufruf `opencode run --format json --model opencode/deepseek-v4.1-flash-free` beantwortete eine synthetische Kurzfrage zweimal. Im zweiten Lauf: Exit 0, 3.267 ms, nichtleeres Text-Ereignis und kein Fehlerereignis. Ein `models opencode`-Aufruf endete dagegen mit Code 1 und listete das Modell nicht; die Ursache dieses Katalogergebnisses wurde nicht weiter bestimmt. Die [aktuelle Dokumentation](https://opencode.ai/docs/models/) enthält einen Hinweis zum Anbieter im abgemeldeten Zustand, der angesichts der erfolgreichen direkten Anfrage hier nicht als Beweis für ein Fehlschlagen interpretiert wird. Freie Modelle können laut [Anbieter](https://opencode.ai/docs/console/models/) zeitlich begrenzt sein.

Ein Aufruf desselben Clients über `stream_free_reply` aus dem aktuellen LastBrowser-Quellstand endete dagegen mit `FreeChatError` ohne Ausgabe. Der CLI-Fallback setzt `--pure`; dieses Flag ist in `opencode run --help` von v2.4.2 nicht aufgeführt, und der direkte Aufruf mit diesem Flag endete mit Code 1. Ob weitere Inkompatibilitäten im Server- oder Streamingpfad vorliegen, bleibt zu prüfen. Das Weglassen des Flags darf erst nach Prüfung der Profil- und Plugin-Isolation erfolgen. Diese Ergebnisse belegen noch keinen Chat im gepackten Browser. Der Testclient wurde nicht in das Produktpaket übernommen.

Der Adapter übernahm zuvor die meisten Umgebungsvariablen des Browserprozesses, darunter potenziell Zugangsdaten oder eine fremde OpenCode-Konfiguration. Der gestartete Free-Client erhält nun nur ausgewählte OS-/Netzwerkvariablen sowie ein eigenes HOME-, Windows-AppData-, XDG- und Temp-Verzeichnis; vorhandene `OPENCODE_*`-Vorgaben werden nicht übernommen. `OPENCODE_PURE` und weitere Einschränkungen werden explizit gesetzt. Der Regressionstest schlug vorher fehl; danach bestanden alle **29 Tests** in `test_opencode_free_chat.py`. Diese Umgebungsprüfung belegt nicht, dass OpenCode 2 alle Plugin- und Tool-Einschränkungen einhält. Das Kommandozeilenflag wurde nicht entfernt und die Windows-Integration bleibt offen.

Ein weiterer direkter Versuch mit v2.4.2 nutzte `OPENCODE_CONFIG_CONTENT` mit `deny`-Regeln für `tool.use`, `plugin.use`, `mcp.use` und `skill.use`. Eine kurze Gratisanfrage antwortete mit Exit 0. Bei einer synthetischen Aufforderung, eine Datei im Testordner zu erstellen, wurde die Datei nicht angelegt; die Ereignisse für `write`, `shell`, `read` und `glob` meldeten Sperrfehler. Allerdings meldete ein `execute`-Ereignis den Status `completed`. Daraus folgt weder, dass eine schädliche Aktion ausgeführt wurde, noch dass wirklich jeder Werkzeugpfad gesperrt ist. Die Plugin-Sperre wurde nicht mit einem aktiven Plugin-Gegenversuch nachgewiesen. Deshalb wurde das `--pure`-Flag noch nicht durch diese Regeln ersetzt. [OpenCode-2-Richtlinien](https://opencode.ai/docs/policies/) beschreiben `tool.use` als Sperre für Berechtigungsprüfungen und nennen für Plugin-/MCP-/Skill-Regeln eine Mindestversion 2.2.3.

Die [OpenCode-Werkzeugdokumentation](https://opencode.ai/docs/tools/) erläutert, dass `execute` Code Mode mit eigenem HTTP-`fetch` bereitstellt und über eine `execute`-Berechtigungsregel separat entfernt werden kann; verschachtelte Tools prüfen weiterhin ihre eigenen Rechte. Ein weiterer Versuch mit zusätzlicher `permissions`-Regel für alle Aktionen erzeugte weder ein Werkzeugereignis noch die Testdatei. Eine harmlose Kontrollfrage scheiterte ebenfalls. Eine Wiederholung identifizierte das Ereignis `provider.free-limit`; damit kann der Werkzeugversuch nicht als erfolgreiche Sperrprüfung gewertet werden. Keine weiteren Gratisanfragen wurden nach Erreichen des Limits gesendet. Eine erfolgreiche Textanfrage und ein aktiver Werkzeug-Gegenversuch mit dieser erweiterten Konfiguration bleiben offen.

Ein gesonderter Plugin-Gegenversuch nutzte ein selbst erzeugtes lokales Testplugin, das beim Laden eine harmlose Markierungsdatei schreibt. Mit demselben isolierten Client und einer ungültigen Modellkennung wurde das Plugin ohne Policy geladen; mit `plugin.use: deny` für `*` wurde es nicht geladen. Beide Läufe endeten wegen des ungültigen Modells mit Code 1; HTTP- und HTTPS-Proxy zeigten auf einen nicht erreichbaren lokalen Port, sodass keine weitere Gratis-Modellanfrage erfolgte. Das ist ein positiver Nachweis für genau diese Plugin-Sperre in v2.4.2, aber kein Nachweis für alle möglichen Werkzeuge oder andere Versionen. Die offene Text- und Werkzeugprüfung mit der erweiterten Berechtigungskonfiguration bleibt bestehen.

Ein zusätzlicher Versuch, diese Werkzeugprüfung gegen einen selbst gestarteten OpenAI-kompatiblen Loopback-Testserver statt gegen ein Gratis-Modell durchzuführen, erreichte den lokalen Server weder im Vergleichslauf noch mit den Sperrregeln innerhalb von jeweils 30 Sekunden. Weitere Gratis-Modellanfragen wurden nicht gesendet.

Die [CLI-Abhängigkeiten](https://github.com/anomalyco/opencode/blob/v2.4.2/packages/cli/package.json) zeigen, dass die MIT-Lizenz des Hauptprojekts allein keine vollständige Bestandsaufnahme der ausführbaren Datei ist. Die Projektlizenz wurde bytegleich zum Upstream-Blob `6439474beed8e0271df9862eff97ffd70ec2464c` unter `docs/legal/notices/opencode-2.4.2-mit.txt` hinterlegt; der Windows-Paketfilter nimmt `.txt`-Hinweise aus diesem Verzeichnis auf. Welche Abhängigkeiten tatsächlich im konkreten Windows-Binary enthalten sind und welche weiteren Hinweise erforderlich sind, bleibt ungeklärt. Die Prüfung ist kein Freigabenachweis für dessen Verteilung.
