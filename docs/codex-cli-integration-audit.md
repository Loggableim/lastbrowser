# Direkte Codex-CLI: lokaler Prüfstand

Stand: 27. November 2026. LastBrowser bietet in den Einstellungen einen Einstieg zum Terminalmodus für eine installierte Codex CLI. `apps/desktop/src/main/terminal-process.ts` startet die ausführbare Datei in einer Pseudoterminal-Sitzung; `NativeTerminalMain.tsx` stellt den Terminalmodus und das Schließen bereit. Das ist eine direkte Terminalanbindung. Daraus folgt nicht, dass Nova-Chat oder Quickchat Anfragen über diesen lokalen Prozess abwickeln.

Auf dem Windows-Testrechner meldete der installierte Client `codex-cli 0.169.0-alpha.11.1`. Mit dem frisch gebauten LastBrowser-Terminalmodul und einem eigens angelegten leeren Codex-Testprofil wurde der echte Client über `startTerminal(..., { mode: 'codex' })` gestartet. Ohne Eingabe einer Anfrage traf Terminalausgabe in drei Blöcken ein; `closeTerminal` wurde akzeptiert, der Prozessausstieg beobachtet und die Sitzung aus der Terminalliste entfernt. Es wurden keine persönlichen Zugangsdaten eingegeben; Proxy-Zugriffe waren auf eine nicht erreichbare Loopback-Adresse eingestellt. Der Test speicherte nur die Prüfergebnisse, nicht den Terminalinhalt.

Die vorhandenen Tests `tests/terminal-process.test.ts` und `tests/codex-settings-wiring.test.ts` bestanden mit neun Tests; sie simulieren den Terminalprozess beziehungsweise prüfen die Verdrahtung des Settings-Codes. Der echte Start-/Stopp-Test belegt keine angemeldete Modellantwort, keinen vollständigen Antwortstream, kein Abbrechen einer laufenden Modellanfrage und keine End-to-End-Bedienung der gepackten Oberfläche. Diese Punkte bleiben für die gewünschte hochfunktionale Anbindung offen.

Ein weiterer isolierter Versuch nutzte denselben CLI-Stand mit `codex exec --json --ephemeral --skip-git-repo-check --sandbox read-only` und einem künstlichen Responses-Server auf Loopback. Der Server sandte zwei Textdeltas mit zwei Sekunden Abstand. Die CLI gab einen `agent_message` erst nach dem zweiten Delta als `item.completed` aus; in diesem Versuch erschien keine frühere Textausgabe. Die Anfrage bot dem Testmodell neun Werkzeuge an. Daher erfüllt dieser konkrete CLI-Aufruf den bestehenden Quickchat-Vertrag einer werkzeugfreien Einzelanfrage mit sichtbarem Streaming nicht. Es wurden keine echten Anfragen an einen KI-Anbieter gesendet.

Der Client bietet alternativ einen als experimentell bezeichneten `app-server`. Mit demselben CLI-Stand wurde dieser mit einem separaten leeren Codex-Profil und einem künstlichen Responses-Server auf Loopback geprüft. Im Streaming-Versuch trafen zwei `item/agentMessage/delta`-Ereignisse bei 4,20 und 7,22 Sekunden ein; anschließend folgte `turn/completed` mit Status `completed`. Im zweiten Versuch wurde nach dem ersten Delta `turn/interrupt` gesendet und bestätigt; bei 4,06 Sekunden folgte `turn/completed` mit Status `interrupted`. Die Prüfungen nutzten `thread/start` mit `ephemeral`, `read-only` und `approvalPolicy: untrusted`; es gab keine echte Anfrage an einen KI-Anbieter. Der isolierte Prüfaufbau liegt lokal unter `source/output/codex-app-server-spike.py` und wurde mit den Argumenten `stream` und `cancel` ausgeführt.

Auch der App-Server bot dem künstlichen Modell neun Werkzeuge an. Diese Versuche beweisen weder, dass Werkzeugaufrufe wirksam ausgeschlossen werden, noch eine Bindung an das gewünschte Benutzerkonto oder die Integration in LastBrowser. Der vorhandene Quickchat verwendet weiterhin die direkte Responses-API, nicht die CLI. Für eine Umstellung müssen insbesondere Werkzeugbegrenzung, Konto- und Profilbindung, parallele Sitzungen, Fehlerfälle und die tatsächliche Oberfläche geprüft werden.

Ein dritter Test (`restricted`) deaktivierte in der isolierten Konfiguration `shell_tool`, `unified_exec`, `view_image`, `apps`, `browser_use`, `computer_use`, `image_generation`, `sleep_tool`, `goals` und `multi_agent` und setzte `web_search = "disabled"`. Die Anfrage bot danach noch `request_user_input` an; zwei Textdeltas und ein regulärer Abschluss wurden beobachtet. Diese Konfiguration ist versionsgebunden und belegt weder einen vollständig werkzeugfreien Request noch das sichere Verhalten bei einem tatsächlichen Werkzeugaufruf. Insbesondere darf daraus keine allgemeine Sicherheitsgarantie abgeleitet werden.

Ein synthetischer Negativversuch (`inject`) lieferte dem isolierten App-Server wiederholt eine künstliche `request_user_input`-Funktionsantwort. Innerhalb des 45-Sekunden-Limits empfing der Loopback-Server 2.050 Anfragen; der Prüfclient beobachtete weder ein entsprechendes App-Server-Rückfrageereignis noch einen Turn-Abschluss und beendete den Prozess. Das Test-Fixture kann fehlerhaft sein: Daraus folgt weder, dass ein echter Anbieter so antwortet, noch dass eine Rückfrage korrekt ausgeführt oder abgelehnt wurde. Für eine Integration sind ein eigenes Zeit- und Anfragebudget sowie ein geprüfter Abbruchpfad notwendig. Der lokale Prüfaufbau begrenzt spätere Wiederholungen des Negativversuchs jetzt zusätzlich auf vier erfolgreiche Fixture-Anfragen.
