# LastBrowser Download Bootstrapper

Native Win32 bootstrapper pinned to the independently verified 0.1.47 setup artifact. This is a local test candidate; it does not update the website, Store assets, or stable feed.

The window embeds the transparent logo, honors the Windows animation preference, lets the user keep the registered install path or choose another existing folder, then reports byte progress through download, verification, and installation. It captures the canonical folder before downloading. After the exact payload hash and Authenticode publisher pass, it runs the existing NSIS installer with `/currentuser /S /D=<validated-folder>`; `/D` is the last, unquoted argument as required by the locally installed electron-builder NSIS template. The native window remains visible throughout. Closing is ignored after NSIS starts, and no mid-install cancellation or rollback is claimed.

The default folder comes from HKCU `Software\e01786d4-bdcb-5140-a133-efc73f0357d3\InstallLocation`, the `INSTALL_REGISTRY_KEY` written by the installed electron-builder template for appId `com.lastbrowser.desktop`; otherwise it follows that template's per-user program-files folder plus `Lastbrowser`. After NSIS exits successfully, **Startklar** requires the registry path to equal the captured path and `Lastbrowser.exe` there to have version 0.1.47, valid Authenticode trust, and the pinned publisher certificate. Only then is **LastBrowser starten** enabled.

Download and verification failures return the same window to a retry-ready state. Cancellation waits for the download worker to finish before offering retry; each attempt has a distinct ID and old worker handles are joined before the next download. The installer starts only after successful verification and a joined download worker. Once NSIS starts, retry and close are disabled until its worker reports completion. These lifecycle changes are source/unit-build verified only; no installer UI or NSIS run was performed.

Build with Visual Studio C++ and Windows SDK using CMake; `MSVC_RUNTIME_LIBRARY=MultiThreaded` selects `/MT`. Configure into a fresh isolated build directory, build `LastbrowserBootstrapper` and `bootstrapper-core-tests`, then run CTest. The tests inject WinHTTP setters and use the same HTTPS redirect and pinned-payload validators called by production through injected file/hash/publisher readers. They reject wrong SHA-256, untrusted or wrong publishers, downgrade/foreign redirects, missing locations, excessive hops, unexpected HTTP statuses, invalid paths, and NSIS argument injection. They also check attempt-ID and worker-join gates, plus the shared fallback policy used when posting a worker result to the UI message queue fails. A dedicated Win32 event wakes the UI message loop to consume that fallback on the UI thread; the worker never mutates window state. `tests/verify-bootstrapper.ps1` checks the pinned local receipt and signed payload, transparent logo, product validation contract, and native imports of the selected output via `-BootstrapperExePath`.

The pinned URL is test tag `test-v0.1.47-20261007-f67320f`, never a stable feed. The existing offline setup and portable downloads remain separate alternatives. Source and local bootstrapper remain unsigned. No runtime UI, release integration, or guest VM acceptance is claimed; clean-VM checks still need to cover appearance, reduced motion, network errors/cancel, silent NSIS handoff, upgrade/profile preservation, uninstall/update behavior, persisted install path, and the final start action.
